# 修复单 25（后端 · 慢工单）：核心代理 ↔ 主代理通信闭环

## 问题（今天实测里真实发生的，都是通信断在半路的样子）

六张工单累计失败，故障形态四次变换（better-sqlite3 版本不匹配 / 状态机迁移缺目标 / 状态机 409 / 任务不存在 404），每一次都要人去翻账本和进程日志才知道原因。这个过程中：

- 核心代理对主代理的结果一无所知：master 视图里有任务列表和回执，但 chief 的对话流里收不到 master 的完成/失败报告，所以它两次误判（宣称「通道不可用」、宣称「我已经修复了」），还编过一次不存在的任务号。
- 失败暴露太慢：派发即死的单卡在 dispatched 等了接近一小时的看门狗。
- 排障信息不回流：mcode 进程的 stderr、模型路由层的拒绝原因，用户和 chief 都看不到。

修复单 21/22 已落地、23 已派（stderr 进过程流 + 上报端点），但它们各修一块——**整条链路从来没有端到端验证过一次**，接缝处的问题只有真实跑一遍才会暴露。这张单的正事就是这个。

## 目标（验收标准：三条路径全走真实链路，不是单测、不是 mock）

1. **金路径**：用户在对话里让 chief 派个小活 → chief 经 create_task 建单派发 → mcode 用登记的模型在项目目录里真实干活（写个 hello.txt 那种量级）→ 过程输出（stdout + stderr）在 UI 里实时可见 → 回执落账 → **chief 在对话里得知结果并向用户汇报**（这一步今天不存在，是闭环的最后一段）。
2. **异常路径 A（起不来/模型被拒）**：任务秒级失败并带可读原因，不等看门狗；chief 收到可行动的纠正指引而不是沉默或编造。
3. **异常路径 B（干活失败/超时）**：失败原因回流到过程输出与事件日志，chief 能向用户转述失败原因。

## 你来定的事

- 链路断在哪几处，自己研究：账本 SQL、pi 会话 JSONL、进程日志都在 `backend/data/` 下。
- 怎么修自己定；与 21/22/23 已落地的改动有重叠或冲突时，自行权衡取舍。
- 验证自己安排：至少测试套件全绿 + 用真实 mcode 把上面三条路径各走一遍（hello.txt 量级即可）。
- 纪律：自测绝不碰真实项目账本——用临时项目、`SPECLOCK2_DATA_DIR` 指向临时目录的隔离实例、或 pytest。
- 这是慢工单：不要求一次到位，可以多轮迭代、多次提交，每轮提交前自己先验证过。

## 背景（已查明的事实，别再踩一遍）

- mcode 必须用它自带的 node 启动（`C:\Users\wowww\.minimax-code\runtime\node-v22.19.0-win-x64\node.exe`），系统 node 会报 better_sqlite3 MODULE_VERSION 不匹配。
- 模型方言分治：pi 用 `minimax-cn`；mcode 命令行要 `--model minimax/MiniMax-M3`（它的路由表只认带 provider 前缀的写法）。
- 派发给 mcode 的任务提示词里不得出现工作台的绝对路径（cwd 由派发参数控制，提示词带路径会污染主代理上下文）。
